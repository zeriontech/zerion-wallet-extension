# Intent-swap Orders are a hash-less arm of the `transactions` store, owned and polled by the background

Swap API v3 can return a Quote whose execution is off-chain: the user signs a Swap Intent (plus a Permit Approval, or after a mined On-chain Approval), the extension posts the signature(s) to `transaction/execute-order/v1` and gets back an opaque order id. Settlement is observed through `transaction/get-order-status/v1` (`pending | successful | failed | rejected`, plus `fills[]` once settled). Everything the extension had for post-signing tracking — the background `TransactionsStore` / `TransactionsPoller`, the UI mirror `localTransactionsStore`, `waitForTransactionResolve`, `getTransactionObjectStatus`, the History merge — is keyed by transaction hash (EVM) or signature (Solana), and an Order has neither until it fills.

We decided two things together. First, an Order is a **third arm of `TransactionObject`** in the same persistent `transactions` store, keyed by its order id, carrying the usual `addressAction`, `from` address and chain, with `hash` written from the first Fill only when the Order settles; status is derived from the Order Status, never from a receipt. Second, the **background owns the Order's whole lifecycle**: a `submitSwapOrder` wallet method calls `execute-order`, persists the pending entry and emits `orderPlaced`; an order poller next to `TransactionsPoller` polls status (fast, then backing off), writes the terminal status and Fill hash, and reports every Fill to `transaction/collect`. The UI signing-queue step only waits on the store mirror, exactly as it does for hashes. Signing itself uses a dedicated `signSwapIntent` method (software) or the Ledger iframe (hardware); both feed the same `submitSwapOrder`.

Why one store and not an `orders` store: History, the pending-transactions count, the UI mirror, ActionInfo and the queue's wait helper all read `localTransactionsStore`; a second store would need a merge layer at every read site, and the pending swap would be missing from History until the backend indexed the Fill. Why background and not the popup (the web app polls from a React component at its root, PR 93 / web ADR-0005): the popup can close the moment `execute-order` returns, and an Order that only lives in popup memory is lost — no History entry, no settlement, no analytics. The extension already answers this for transactions by tracking them in the background; Orders follow the same rule.

Considered and rejected: a UI-side `OrderPoller` like the web app (dies with the popup); a separate `orders` store (clean type, duplicated plumbing); registering a normal transaction only after the Fill arrives (History shows the swap late, nothing survives a service-worker restart); converting the settled Order into a regular EVM/Solana entry keyed by the Fill hash (the Fill is often broadcast by a relayer, so `from`-based filtering and nonce purge would misbehave).

Consequences worth knowing: Orders have no nonce, so they age out on the time-based retention like Solana entries instead of being purged by nonce; `performPurgeCheck` must skip hash-less items rather than bail out (it currently `return`s on the first one); `upsert` keys become `hash ?? signature ?? orderId`; `filterAddressTransactions` reads the Order's own `from`; `TransactionsFeature`-style receipt polling never starts for a Fill hash. `QueueEvent` gains `step-requoting` and `step-order-pending { orderId }` so the HardwareDialog can render "Refreshing quote" and the order wait (the toaster ignores intra-step phases and keeps "Swapping"); the queue's bounded wait (same budget as a transaction) ends in a neutral "Still processing" terminal while the background keeps polling.
